# tetherphp-demo — a TetherPHP example application

A small notes application built with [TetherPHP](https://github.com/Dillonsmart/tetherphp), to show what a real
feature looks like once it has a database, forms and validation behind it. Every file here was either generated by
`tether make:resource` or written by hand to fill in the `// TODO` the generator left, and the commit history shows
which was which.

It does one thing: notes with a title and a body, listed, shown, created, edited and deleted.

## Running it

Requires PHP 8.5 and Composer.

```bash
composer install
cp .env.example .env
php tether db:schema        # creates storage/notes.sqlite from database/schema.sql
php tether serve            # http://127.0.0.1:8000
php tether test             # 21 tests, against an in-memory database
```

## What to read, in order

The whole application is one feature, `Note`, and every piece of it is a directory or a file named for what it does:

```
routes/web.php                      the seven routes, exactly as make:resource printed them
app/Services.php                    what the app is made of: Env, Log, and a PDO — built in public/index.php
app/Actions/Note/                   one class per route; each hands its Domain a Notes and what it read off the request
app/Domains/Note/Notes.php          every SQL query, in one place, handed to the Domains that need it
app/Domains/Note/Attributes.php     the rules a note must meet — the whole validation layer
app/Domains/Note/Results/           the four shapes a Domain answers with: Collection, Record, Written, Invalid
app/Domains/Note/Store.php          reads the payload, checks it, writes it or refuses it
app/Responders/Note/Store.php       a redirect for a write, the form again with a 422 for a refusal
app/Views/partials/note-form.php    one form for create and edit, with the errors beside the fields
database/schema.sql                 the schema; php tether db:schema applies it
tests/Feature/NotesTest.php         every route, through the real Kernel, against an in-memory SQLite
```

## The three things worth noticing

**How the database reaches a Domain.** There is no container. `app/Services.php` lists what the application is
made of, `public/index.php` builds it, and the Kernel hands it to every Action. The Action passes its Domain the
piece it needs — a `Notes` over the `PDO` — never the whole object, so `Domains\Note\Store` has a constructor that is
the complete list of what it depends on, and its unit test hands it an in-memory SQLite.

**How a refused write gets back to the form.** `Store::handle()` returns `Written|Invalid`. The Responder picks the
answer off the type: a `Written` is a 303 to the new note, an `Invalid` is the form re-rendered with what was typed
and what was wrong with it, as a 422. There is no flash session, no redirect-back, no validator object — one result
type per outcome, which is the same rule that makes a missing note a `404` rather than a `found` flag.

**How much of it was generated.** `tether make:resource Note --uri=/notes` wrote the Actions, Domains, Results,
Responders and views and printed the seven route lines. What was written by hand is the SQL in `Notes`, the two
rules in `Attributes`, and the views' markup. This application was built against core v0.11, before the generator
wrote `Invalid`, `Attributes` or whole-page views; core v0.12.0 now generates all three in exactly this shape,
because this is where the shape came from. Run `php tether explain /notes/12` or `php tether context` to see the
application describe itself.
